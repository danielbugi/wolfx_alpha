# Ledger research data availability matrix

Status: read-only audit, 2026-10-22. Production `trading_production` was read through sessions forced read-only. Code is `origin/main` `f3b88d9`. Nothing was changed.

**Scope:** the dimensions and metrics `mechanism/strategy_analytics/performance.py` declares unavailable (`UNAVAILABLE_DIMENSIONS`, `UNAVAILABLE_METRICS`), plus "declared exit rules".

**Ledger baseline:**
- `signal_ledger` holds 2,973 rows over 16 sessions (2026-09-28 → 10-21).
- 1,468 rows (sessions 10-09 onward) carry `observation_id` / `feature_snapshot_id`.
- No row has 20 forward bars yet (prices end 10-21). The first full horizons arrive about 2026-10-26.

**Value classes** used below:

| Class | Meaning |
|---|---|
| **OBSERVED** | Captured forward by our own job, with a database-stamped time |
| **DERIVED** | Computed now from observed prices, using only data available at the stated time. Legitimate when the inputs are prices. |
| **RECONSTRUCTED** | Recomputed for the past from inputs that were not point-in-time, e.g. modern sector membership. Must be labelled. |
| **RETROSPECTIVE** | A vendor value as it is now, used for a past moment |
| **UNAVAILABLE** | No legitimate source |

The live ledger uses the **1R first-target** rule (close entry, no gaps, no cost). The 9-year backtest `r_single` is the **3R** rule. Nothing below mixes the two.

## Things the matrix found that are wrong today

1. **Stale capability flags.** `definitions.CAPABILITIES` marks `forward_return_labels`, `candidate_observations` and `feature_snapshots` as **unavailable (Release B)**, but production holds 29,427 labels, 14,629 candidates and 14,629 snapshots. The API under-reports what exists. Fix: make these flags data-driven or update them (small code change).
2. **The `UNAVAILABLE_DIMENSIONS` requirements text is partly outdated.** For example, `relative_strength` "requires sector_snapshot / feature_snapshot (migrations 22, 24)", but observed `stock_relative_strength` (rs_v1) now exists. Market regime and RS are **joinable now for 46% of ledger rows** (1,359 / 2,973).
3. **The `'unknown'` model_version** (387 rows) still makes ML coverage read as non-zero.
